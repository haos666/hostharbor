# 同类项目研究：值得借鉴什么，HostHarbor 保留什么

> 后续选择（2026-10-26）：用户已确定优先做加密备份/恢复、SSH 配置导入和单台服务器常用操作。本文 R1–R3 保留为研究建议，暂不实施；当前计划见 [个人工作流](../../personal-workflow-plan.md)。

研究日期：2026-10-26。首轮源码研究与受限验证完成；尚未进入产品代码实施。

**建议保留现有架构，复用设计与测试方法，不整体替换审批引擎。** 五个项目里，Kino 最接近桌面产品形态；ssh-mcp 的批准失效、拒绝解释与性质测试最值得深入借鉴。adremote 的变更计划、Termix 的动作目录适合作为后续能力设计参考。

## 最重要的结论

| 项目 | 适合借鉴 | 不直接采用 |
| --- | --- | --- |
| [Kino SSH Manager](projects/kino.md) | 完整命令 + 倒计时 + 批准范围；每小时活动预算；受管文件备份 | 复制 MCP 凭证库、仅进程级会话批准、结束后整体写 cast；GPL 源码不并入本项目 |
| [ssh-mcp](projects/ssh-mcp.md) | TTL/generation 批准缓存；具体拒绝原因；性质测试；传输 idle 机制 | 整套分类器、客户端审批长时间挂起、无持久化配额模块直接照搬 |
| [adremote-mcp](projects/adremote-mcp.md) | 目标/目的/验证分开的计划；文件变更前后哈希与备份材料 | 智能体可调用的批准步骤当作人工证明；缺少原文件基线复核的写入链路 |
| [mcp-ssh](projects/mcp-ssh.md) | 目的说明、cwd、日志事件关联 | 持久 Shell、命令名白名单、超时放行；独立许可证材料尚需确认 |
| [Termix](projects/termix.md) | 全局/主机动作目录、资产树容错、多语言设置目录 | 当前引入整套插件/同步/多用户平台；本轮未验证独立插件实现 |

## 我们应继续走的方向

让外部智能体先准确选择服务器，再使用可维护的应用/部署/日志上下文，最后通过统一执行服务完成操作。用户看得懂目的、影响、审批依据、进度和证据；出现异常知道该等、该检查还是该重新确认。

我们的异步操作 ID、幂等与版本重检、加密分块回放、独立传输审批、档案/应用索引已经具备基础，不因参考项目有同名功能而重做。这里描述的是自己的产品重点，不宣称其他产品全部没有。

首批建议：

1. **审批更可理解，并可精确短时批准**：具体片段/参数解释、智能体目的说明、严格绑定范围的可选短时授权；破坏性操作保持人工。
2. **策略性质测试**：从用户发现一个补一个，转为系统检查组合、引用、包装和审批失效条件。
3. **可选活动预算**：让用户限制某个接入持续重复操作，保持现有宽松默认体验。

详细范围、验收与后续候选见 [复用提案](reuse-proposals.md)。受管变更预览/备份、全局检索与分组放后续；不是现在就把产品扩成终端平台。

## 实际验证与边界

- 五个仓库均已克隆并记录固定 SHA；已审查列出的核心路径。
- ssh-mcp 四个纯策略测试文件：**146 项通过**。
- HostHarbor 六个相关测试文件：**327 项通过**，含合成 SSH/SFTP fixture；这次不是重新运行全部 870 项。
- 十条合成命令做了纯函数观察，没有执行这些命令。单文件删除在对方分类器是 safe，我们宽松模式要求审批；说明不能把对方类别直接当成本产品放行依据。
- 没有运行第三方桌面 GUI、Windows/Linux 原生验收、真实客户端审批或同环境大文件性能对比，不对这些方面作已验证结论。
- 没有访问用户服务器、生产凭证或外部 AI；没有修改产品代码、增加产品依赖或推送 GitHub。
