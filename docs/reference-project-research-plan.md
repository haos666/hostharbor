# HostHarbor 同类项目研究与复用计划

创建日期：2026-10-26（Asia/Shanghai）。

状态：**首轮源码研究与受限验证已完成，产品实施未启动。** 报告入口：[研究总结](research/reference-projects/README.md)。本轮未改产品代码、未推送 GitHub；完整第三方 GUI、原生跨平台与真实客户端验收仍未完成。

## 1. 目标与产品方向

研究同类项目已经解决的问题，选择适合 HostHarbor 的交互、协议设计、执行机制和测试方法，减少重复探索。每个候选都需要回答：解决哪个现有问题，证据是什么，适配成本多大，为什么值得引入。

HostHarbor 继续围绕个人安装的桌面工作台：本地保存凭证，为外部智能体提供受控 MCP，维护服务器与应用上下文，让用户能够理解、审批、追踪操作并检查结果。研究不自动扩展为企业平台、云同步、多机批量执行或完整交互终端建设。

优先方向作为待验证假设：

- 接入外部智能体的步骤更少，权限和目标范围更清楚。
- 服务器档案、应用别名、部署路径和日志入口能被智能体有效复用。
- 日常操作顺畅，危险操作的审批理由具体，失败和未知结果可解释。
- 传输、审批等待、断线和应用重启等长流程有明确状态与恢复路径。

## 2. 研究对象

以下来自前一轮仓库检索，是候选对象，**不是已验证的能力清单**。正式研究时重新确认默认分支、版本、许可证和可运行状态，并记录固定 commit SHA。

| 顺序 | 项目 | 重点调查的问题 |
| --- | --- | --- |
| 1 | [Kino SSH Manager](https://github.com/Samarthegde/kino-ssh-manager) | 桌面凭证管理与 MCP 如何衔接；暴露主机、停止接入、审批和回放的完整流程；文档与实现是否一致 |
| 2 | [ssh-mcp](https://github.com/tufantunc/ssh-mcp) | 命令分析、授权与审批如何组合；破坏性操作、复杂 Shell、提权和异步执行如何表达 |
| 3 | [adremote-mcp](https://github.com/nqmn/adremote-mcp) | 计划与批准执行是否分离；批准绑定哪些内容；文件修改、备份与校验如何处理 |
| 4 | [mcp-ssh](https://github.com/xiongjiwei/mcp-ssh) | 持久会话的目录/环境状态；审批等待和超时；日志关联与输出限制 |
| 5 | [Termix](https://github.com/Termix-SSH/Termix) | 资产、凭证、文件和日志的交互组织；桌面独立运行边界；可借鉴的组件设计与扩展机制 |

首轮先完成前两个。后面三个针对已有疑问取证，不以收集更多项目或追齐功能数量为目标。仅在发现明确缺口时增加研究对象并说明原因。

## 3. 比较维度与证据要求

| 维度 | 必须回答的问题 |
| --- | --- |
| 接入与凭证 | 智能体拿到什么；凭证在哪一层使用；Token 的保存、复制、修改、撤销和到期如何处理 |
| 目标与上下文 | 如何发现并确认目标机器；档案是否结构化、可编辑；过期信息和同名应用如何处理 |
| 命令与提权 | 独立命令还是持久 Shell；目录怎样确认；sudo 如何传入凭证；秘密是否进入命令、输出或记录 |
| 审批 | 什么情况下转人工；复杂命令为何被拦；批准是否绑定不可变内容；等待、过期及通知如何处理 |
| 长任务与结果 | 客户端超时后如何继续查；断线、取消、重启如何区分；是否错误地重试未知结果 |
| 文件传输 | 上传目录、大小限制、进度、分阶段超时、哈希校验、临时文件发布和失败恢复怎样实现 |
| 记录与回放 | 记录哪些字段；输出如何分块、限流、保留和清理；是否把普通日志误称为防篡改审计 |
| 桌面交互 | 初次接入、列表筛选分页、详情、空态、固定布局、通知、键盘焦点与中英文长文案 |
| 工程与交付 | 进程边界、测试场景、协议兼容、升级/迁移、打包签名和原生平台验证 |

证据分级：`文档声称`、`源码确认`、`测试确认`、`隔离实测确认`。未找到证据写“未确认”，不能直接写“没有”；README、源码和运行结果冲突时单独列出。

源码结论使用固定 SHA 的文件/行链接。每个判断记录研究日期、版本、平台和适用限制；不根据 Star 数或宣传文案判断安全性与成熟度。

## 4. 用同一套合成场景比较

全部使用合成服务器与凭证，测试资产名固定为 `fixture-host-a` / `fixture-host-b`，应用名为 `fixture-app`。不使用用户真实资产或生产凭证。

1. **首次接入**：创建凭证、绑定一台主机、核对指纹、创建最小范围接入，智能体发现目标。
2. **目标歧义**：精确命中、多个候选、明确全部、带筛选条件的全部；检查是否越出本次任务范围。
3. **应用诊断**：询问 `<目标服务器>` 上 `<应用>` 登录失败的日志，检查是否复用档案、定位入口、限制输出并给出证据。
4. **复杂日常命令**：查询组合、管道、格式化输出、重定向、配置修改、安装及应用重启，记录审批原因和交互次数。
5. **破坏性操作**：删除、系统重启/关机及磁盘破坏命令，仅在解析/审批层或可销毁环境验证，不在真实主机执行。
6. **审批等待**：长时间无人处理、到期后批准、请求重复提交、批准前目标/授权变化，检查是否重复或错误执行。
7. **提权与撤销**：独立 sudo 凭证、密码错误、授权撤销、主机指纹变化、应用界面锁定，检查行为与策略是否一致。
8. **传输与异常**：小文件、大文件、校验慢、连接断开、目标已存在、磁盘不足；检查阶段、临时文件和最终结果表达。
9. **历史与重启**：查询记录、回放、保留期清理；应用重启后检查进行中任务如何恢复或标记未知。
10. **中英文与窄窗口**：对比关键流程的溢出、遮挡、焦点、空态和通知。

每个场景记录操作步骤、预期/实际行为、必要交互次数、等待方式、审批原因、结果证据及问题。性能比较须使用相同环境并记录文件大小、网络条件和校验方式；不比较不可复现的速度数字。

## 5. 复用决策

“复用”分为四类，不默认等于复制源码：

| 类型 | 适用方式 | 决策要求 |
| --- | --- | --- |
| 交互或设计思路 | 学习流程，按 HostHarbor 架构独立实现 | 写明原问题、参考证据与自己的实现取舍；不用他方品牌素材 |
| 测试方法 | 将有价值的边界场景转为本项目测试 | 检查是否允许复制具体测试代码/数据，默认用合成 fixture 重写 |
| 第三方依赖 | 引入有维护价值的通用库 | 评估许可证、传递依赖、漏洞、平台兼容、包体及维护成本 |
| 源码片段/模块 | 仅限明确适配且授权条件清楚的候选 | 记录来源 SHA、文件、许可证、版权/NOTICE、修改和更新责任，再决定是否采用 |

正式复用前，核对目标版本中相关文件和依赖的实际许可证，不只看仓库首页标签。HostHarbor 当前采用 Apache-2.0；遇到 GPL/AGPL、未授权或边界不明确的源码候选，先标记为授权待决，未经兼容性确认不得并入发布代码。可先研究公开行为与设计，独立实现仍须记录来源与边界；必要时另行咨询专业意见。

所有候选标注：`采用思路` / `直接复用候选` / `补充验证` / `暂缓` / `不采用`，并说明理由。不能为了复用而绕过现有凭证保护、授权重检、主机身份验证和执行意图持久化；不能把命令黑名单或 AI 分类当作完整安全边界。

## 6. 执行阶段与交付物

- [x] **阶段 0：计划归档。** 建立本文件并在主计划添加入口。
- [x] **阶段 1：基线与许可。** 冻结 HostHarbor 基线 SHA；记录五个参考项目的 SHA、许可、安装前提和已确认能力。先不运行未知安装脚本。
- [x] **阶段 2：重点项目分析。** 优先 Kino 和 ssh-mcp，沿实际调用链查源码、测试和相关 Issue，整理优势、限制与失败路径。
- [ ] **阶段 3：定向补充与隔离实测（部分完成）。** 五项目定向源码取证已完成；ssh-mcp 146 项纯策略测试、HostHarbor 327 项相关测试和十条纯函数观察已完成。第三方 GUI、跨平台、真实客户端及大文件性能仍待独立环境验证，详见报告基线。
- [x] **阶段 4：比较与复用提案。** 形成证据矩阵和排序清单；每项写清用户收益、HostHarbor 差距、依赖、成本、风险、授权条件与验收场景。
- [ ] **阶段 5：确定首批落地。** 选择最多三个收益明确且范围可控的改进，与用户确认实施范围，再更新主计划和架构决策。
- [ ] **阶段 6：逐项实施与复测。** 后续另开实现任务；保持中英文同步，按改动运行 `npm run check` 和必要原生验收，按大版本批量交付 GitHub。

研究启动后在 `docs/research/reference-projects/` 下逐步产出，不预先创建空报告：

- `baseline.md`：本项目/参考项目 SHA、平台、许可和验证状态。
- `projects/<project>.md`：逐项目证据、优点、问题和适用边界。
- `comparison.md`：同场景对照与证据等级。
- `reuse-proposals.md`：有排序的复用提案和“不采用”的原因。

按用户 2026-10-26 的后续指定，五个参考仓库浅克隆到 `<github-work>/<仓库名>`；临时观察 harness 与原始测试输出放入已忽略的 `work/`；文档只引用脱敏证据，不提交凭证、用户路径、真实主机信息或完整外部仓库副本。

## 7. 完成标准与接续方式

研究完成意味着：能基于可追溯证据说明值得借鉴的内容、不能直接复用的内容，以及 HostHarbor 首批最多三个改进的具体收益和验收方法。功能清单相似不等于验证通过，也不自动触发代码合并。

用户后续已选择加密备份/恢复、SSH 配置导入和单服务器常用操作，见 [当前实施计划](personal-workflow-plan.md)；R1–R3 暂缓。后续研究读取总结和基线，不重复已完成的源码审查；完整产品实测从阶段 3 的未验证项继续。**本计划不创建定时任务，也不在用户未启动时自动执行研究。**
